# Visual exploration and selection

## Make the differences meaningful

Begin with the verified project brief and existing identity, not a favorite palette. Derive motifs from real artifacts: a note index, terminal rhythm, a material specimen, a data transformation, a map or an actual interface.

Prepare 2–3 project-specific directions. Do not name them from a fixed menu used for every project. Vary at least two of:
- Composition and focal point.
- What proof leads the page.
- Type hierarchy and reading rhythm.
- Visual language, material or motif.
- Density and image treatment.

Keep product facts consistent across the options. A screenshot-led composition, an editorial artifact layout and a precise input/output study could be genuinely different for one project; those are examples, not a required trio.

## Deliver a choice the user can see

Each option includes:
- A rendered first-screen sketch at a comparable size.
- A short name tied to this project.
- The idea and evidence it foregrounds.
- Proposed production method: screenshot, SVG, generated art or composition.
- A concrete tradeoff, such as screenshot legibility versus expressive atmosphere.

Use existing artifacts for drafts. If placeholders are necessary, visibly mark them. Conceptual art is not a fake screenshot. Keep sketches lightweight; do not spend full production effort on every alternative.

Show the options together when possible, but also make each readable individually. Text descriptions alone are not previews. With no rendering capability, explain that limitation and ask whether text-only concepts are acceptable.

Recommend one and wait for the user's selection. Record the chosen direction and feedback in working notes. Silence is not a choice. If the user already supplied a direction or explicitly delegates selection, use that authorization without a redundant question.

## Turn the choice into production decisions

Record palette roles, font approach, layout, motif, image treatment, density and media choice. Do not ask users to approve every implementation detail once the visual intent is clear.

Use the selected system across cover, icons, screenshots, captions and optional section imagery. Do not add a decorative graphic to every heading.

Make the cover recognizable without hiding the project. Test whether removing its name would leave a generic asset suitable for an unrelated repository; if so, use more project-specific material.

Do not promise web layouts that GitHub Markdown cannot reproduce. Exact body typography and arbitrary CSS grids belong to a website, not a README. Build identity through supported image assets, content hierarchy and restrained Markdown.
